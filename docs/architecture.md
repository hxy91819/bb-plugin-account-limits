# Source architecture

```text
Host-local optional CLI Proxy -> normalized provider snapshot -> SQLite cache --+
BB Account Pooler public RPC -> normalized provider snapshot -> owner cache ----+-> source registry -> dashboard
                                                                              +-> source-specific refresh
```

The domain types are `QuotaAccount`, `ProviderSnapshot`, `QuotaSourceId` and `AccountLimitsPanelSnapshot` in `contract.ts`. The older `cliproxy*` wire names are retained only for upgrade compatibility. Sources own availability, discovery, authentication, errors and caching; the shared UI owns cards, folds, account/pool aggregation, recovery segments and weekly pacing.

- `sources.ts`: small `QuotaSource` interface and registry. Selects one source for targeted refresh, skips explicitly unavailable adapters and isolates failures.
- `config.ts`: host-local optional configuration. The default proxy is `null`; no executable paths or account identities are embedded.
- `host.ts`, `usage.ts`: CLI Proxy adapter. `cliproxyStatus` reads configuration only. Unconfigured hosts do no quota I/O. Tokens are substituted by CLI Proxy for authoritative usage endpoints; verified cached signals are a fallback. Antigravity discovers its project/plan and reads `retrieveUserQuotaSummary` on `daily-cloudcode-pa` with the versioned `antigravity/hub/2.9.1` compatibility identity. A bare user agent can omit Gemini on daily, while production can return untouched Gemini placeholders for active daily accounts. Valid complete daily data, including real zero usage, stays authoritative. An incomplete or unusable daily summary may query production once: missing families are appended without replacing measured daily families; a failed fallback retains usable daily data. Authentication/rate-limit failures and cancellation are not retried. Model catalog discovery is independent of quota summary selection.
- `server.ts`: host discovery, proxy cache and public RPC/CLI wiring. `createPanelSnapshotReader` checks host configuration before considering cached quota; removing configuration clears old proxy rows. Empty config does not become an error source. Hosts with no previous data and no reachable adapter stay absent.
- `native-provider-panel.ts`: discovers usage-capable providers on each connected BB machine and calls the public `system.usageLimits` maintenance API per provider. No separate login or proxy configuration is needed. Authentication and failures stay provider-local; targeted refresh preserves other providers. The verified built-in Codex and Claude maintenance handlers fetch upstream usage on every request, so successful collections record their local completion time and can support weekly pacing. Other providers have no freshness guarantee in this API and retain null timestamps, including forced reads. Discovery failures retain the previous observation with a cache warning. Accounts on different machines remain separate.
- `account-pool-panel.ts`: consumes only Account Pooler's public `provider-usage.v1.listResources/getResource`. An unavailable installed source retains its last observation with a warning. Account Pooler is listed only once because it is shared across machines.
- `usage-source.ts`: exposes only proxy resources to BB's native Provider Usage consumer; it does not export Account Pooler back into itself. Discovery is cache-only. Existing resource IDs are retained.
- `pool-reset.ts`: selects the earliest reported weekly reset batch, retaining unused accounts and each individual remainder/state. It reuses per-account weekly pace quality checks, keeps overdue observations pending, and marks unreported reset times explicitly.
- `pool.ts`, `pool-recovery.ts`, `weekly-pace.ts`: pure shared calculations. Sources and independent window identities are never combined. Missing all-model weekly quota is isolated, not interpreted as unlimited.
- `quota-presentation.ts`, `quota-ui.ts`: shared frontend snapshot/request deduplication, browser-scoped failure/reminder preferences, presentation-only filtering and threshold-crossing tracking. Each tracker quietly seeds its first usable snapshot, including when browser history is absent or unreadable; empty, failed and overdue-only startup observations do not consume this baseline. Windows discovered later are also seeded quietly on first observation. Only subsequent observed crossings produce toasts. Reminders reuse the shared account/legacy adapter, `groupAccountPools` and `aggregateCliproxyPool`, with independent source/machine/provider/type/window identities and the same capacity weights as the pool view. Only complete, non-overdue pool windows produce observations; an individual exhausted account does not notify on its own. A failed account has no reliable tier in the DTO, so its provider temporarily produces no reminder observations. An empty observation with a known tier suppresses that tier across Claude availability subgroups; an unidentified empty observation suppresses the provider. Display grouping stays unchanged, and suppressed observations do not overwrite the last complete reminder history. The alert title names the resource pool and reporting-account count. History keeps the versioned localStorage key `account-limits.alert-history.v1`; new pool keys are distinct from old account keys and quietly establish their own baseline. A common known reset across all members is a pool cycle; staggered resets only re-arm after the aggregate drops below a threshold, preventing duplicate notifications when the earliest reset changes. Account order, labels and view/display preferences do not change alert identity. The tracker validates persisted data and falls back to per-page memory when storage is unavailable; no credentials or quota snapshots are stored in this history. When a connected, error-free Account Pooler has usable Codex windows, the shared presentation layer prefers it over native Codex entries for both panels and reminders; a failed or empty pool restores native entries. Other providers such as Cursor SDK remain visible. Raw observations and provider routing are unchanged. Compact service cards reuse `groupAccountPools` and `aggregateCliproxyPool`, summarize weekly budgets before session/model windows, keep independent families explicit, and derive pacing colors from each pool. Generous pace uses the theme success color in cards, badges, values and bars; each model family carries its own pace and hover label. Cards and full/compact meters share `quotaTone`: remaining <=10% is critical, blocked/conserve is warning, generous is success, other remaining <=20% is warning, otherwise neutral. This order is independent of used/remaining display mode, so a generous pool with 15–20% remaining stays green in every view. Session exhaustion retains its separate warning. A mixed Claude card shows only the measured all-model weekly pool, marks incomplete account coverage with `*`, and explains excluded accounts both in its hover detail and a visible selected-card note with reporting/total account counts; it does not infer missing quota or combine model caps. If no total week is reported, the card remains unknown. Any partially covered summary window carries the same marker. Expanded details retain the separate missing-total-week pool. They stay pooled when expanded details switch to accounts. Legacy flattened windows are first grouped by their account labels. The app-wide monitor refreshes visible windows every five minutes and cleans up timers/listeners on unmount.
- `app.tsx`, `panel-styles.ts`: source-level native disclosure controls, scoped host-token CSS, source/provider refresh, theme-aware custom SVG glyph. Fold state is local to this browser and independent of account/pool and display mode. Compact cards put the tier before a service short name and wrap into rows at a readable minimum width; model-family labels stay on one line. Compact used/remaining and account/pool controls share the existing browser preferences and never fetch quota. Native inline disclosures expose pacing reasons and reset-account details to touch and keyboard users; toggling them does not fetch quota. Coarse-pointer action targets grow to36px. Weekly quota leads; session and model-cap rows share a hanging-indent template and typography. Account views in both panels order accounts by the earliest upcoming weekly-budget reset (across model families). When no weekly budget is reported, other budget/model-cap windows take precedence over 5h, and 5h is used only when it is the only window kind. A present weekly window with an unknown reset stays unknown rather than borrowing its session reset. Overdue records follow upcoming resets; unknown or failed records come last, with ties retaining source order. Sorting is presentation-only, includes legacy flattened accounts and never mutates source snapshots or pool inputs.

## Required pool compatibility rule

Weekly budgets lead the full and compact views. `quotaWindowPeriod` pairs raw and pooled 5h/weekly labels within the same model family and preserves model suffixes supplied by adapters. The shared renderer shows 5h as subordinate status, without a competing main bar, while retaining percentage, reset, coverage and exhaustion warnings. Missing weekly quota stays unknown and 5h never substitutes for it in compact summary cards. Claude model caps retain their separate denominators beneath the shared total week. These are presentation rules; source snapshots, window IDs, recovery and pacing calculations are unchanged.

Every pool's complete capacity is 100%. The existing weighted mean remains authoritative; pooled percentages display up to one decimal and show the cohort account count once at the pool heading. Fully covered windows do not repeat account counts or coverage ratios; a partially reported window explicitly shows its reporting count and coverage fraction, and exhausted-window counts remain visible. For equal weights, 1%, 18% and 0% used become 6.3% used of the three-account pool, not 19% of the pool. Coverage still excludes missing observations and identifies partial results; no absolute token capacity or independent subscription count is inferred.

By default, pool accounts only within the same account type and subscription tier. Google AI Ultra and Google AI Pro remain separate even when they share a source or quota-window name. The source-local CLI Proxy Claude weekly policy below is the explicit exception; no other source or model family gains cross-tier pooling.

`groupProviderAccountTypes` gives verified CLI Proxy Claude Pro, Max 5x, Ultra and legacy Max 20x a stable `claude-weighted-weekly` pool, alongside Team accounts with a reported numeric multiplier. The weekly ratios are 1/5/10; Team uses its reported multiplier as an explicitly estimated weekly ratio (Team 5x means estimated 5). The group label says when estimates are included, and its visible capacity note lists the ratios and their scope. Raw account views retain their original windows, timestamps and identities. Unknown plans and Enterprise keep the default tier boundary. Missing total weeks still form the existing availability subgroup and partial coverage remains visible.

Only the computed `PoolAccount` inputs carry a weekly capacity factor and `poolWindowIds` selecting reported all-model weekly identities (normally `7d`, retaining explicit source IDs). `aggregateCliproxyPool` respects that selection; it does not apply weekly ratios to 5h or model caps. Each computed weight is the source account weight multiplied by its weekly ratio. These inputs retain all raw windows so pacing still sees session exhaustion, while reset/recovery use the same weekly denominator. They never enter DTOs, source caches or routing. The compact selector uses the provider-aware types with raw accounts; full/compact pools, reminders and public Provider Usage use provider-aware grouping. Public combined-pool IDs are distinct from old per-tier IDs, and old resources fail lookup instead of selecting a new pool silently.

Apply this boundary before computing percentages, reset/recovery forecasts and weekly pacing. The full dashboard, compact service cards and exposed pool summaries must use the same grouping, while retaining the existing source, model-family and missing-total-week boundaries.

`groupAccountTypes` in `pool.ts` normalizes source-reported `planLabel` (case, whitespace and cached suffix); `groupProviderAccountTypes` applies the Claude weekly exception before `groupAccountPools` performs the availability split. Account identity labels, absent plans and failed queries remain unidentified, separate from known plans. Existing unidentified-only data retains its legacy grouping. No unreported plan or official capacity ratio is guessed; the explicit Team estimate is always labeled.

The CLI Proxy Claude adapter fetches `/api/oauth/profile` alongside usage through management token substitution. Its plan label includes the organization family and reported rate-limit multiplier/tier, plus Team/Enterprise seat tier. A Team credential using a Max-named tier remains Team. Legacy personal Max 20x and the explicit Ultra organization family normalize to Ultra under the official migration; its weekly ratio is 10, not 20. Missing Max multipliers are not guessed; profile failures preserve valid usage, and cached limits retain verified plans with the cached marker. Raw profile identities and response metadata are not exported.

Full-panel pool sections and compact service cards use these same type boundaries. Compact cards select and show details for one type; model-family windows remain separate within each card. Coverage and partial-data stars count only that type. Public quota resources use stable type-qualified pool IDs; existing account resource IDs are unchanged. Legacy untyped pool IDs remain valid only for the unidentified cohort, and removed or changed pools fail lookup instead of silently selecting a different tier.

To add a source, extend the source ID schema, implement a `QuotaSource` adapter returning normalized accounts with stable window IDs and real observation times, register it in the server and add its presentation name. Include tests for absence, source failure, targeted refresh, incomplete measurements and model-window identity. Do not embed another service's authentication or storage rules into shared pool logic.

No live tokens, prompts, machine addresses, named personal accounts or agent launch wrappers are packaged. The host must be able to reach its configured service; a UI client does not need that access. Credentials remain host-local. Source Git installs are built by BB; release archives also include the generated portable bundles and their SDK metadata.

Execution adapters must be installed independently of this dashboard. ACP launch commands, environment values, skills and supported controls belong to BB's `acp-extensions.customAgents` settings. Optional compatibility adapters run as separate executables; this dashboard never registers them. Disabling or upgrading this dashboard must not unregister those providers.
